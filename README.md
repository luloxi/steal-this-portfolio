# ¡Robate este portfolio! 🦝

Un esqueleto de portfolio. El nombre, los textos, los proyectos y los colores salen de D1 y se editan en el modo admin, no desde GitHub. Un deploy de ejemplo está en **https://lulox.com.ar**.
Un portfolio simple y bilingüe (ES/EN) con blog, editor inline para el admin y un formulario de contacto simple, todo en un solo Cloudflare Worker.
Forkealo, cambiá el contenido y publicalo. Esa es toda la idea. ✨
Es copyleft a propósito: llevátelo, mejoralo y dejalo abierto para el que venga. 🏴‍☠️

## ✨ Qué trae

- 🏠 **Inicio**: landing que scrollea con un header fijo con blur suave (`src/components/home-header.tsx`): LULOX, links de texto sin pastillas (Sobre mí, Automatizando, Servicios, Proyectos, Blog, Contacto) que se marcan con un subrayado mientras scrolleás por su sección, y Contratar como único botón; en celular y pantallas angostas, botón de menú con links grandes. Después: propuesta corta, **Sobre mí** con foto vertical que ocupa el alto de la tarjeta (arriba y a lo ancho en celular), **Automatizando procesos** (seis mini demos animadas, sin videos), ejemplos, servicios, **Proyectos** (solo Malito y Garpen, con un video corto en loop y una línea; Tarask, DJTube, Mochi, SAMI, PunkSociety y Steal This Portfolio quedan solo en `/proyectos`), las últimas notas del blog, cómo es trabajar conmigo, FAQ y cierre con Contratar. En tema claro los acentos son pasteles vivos (coral, cielo, menta, limón, lila) con texto AA; el oscuro sigue en neón. Animaciones al scrollear; con `prefers-reduced-motion` todo queda quieto y los videos muestran solo su captura.
- 🧭 **Servicios por necesidad** (`/servicios/<slug>`, `/en/services/<slug>`): agentes de IA, automatización de procesos, CRM a medida, Grok Bot, y WhatsApp y mail. `/servicios/automatizar-finanzas` redirige con 301 a `/servicios`. Cada una con respuesta directa, casos de uso, cómo trabajo, FAQ y Contratar.
- ✍️ **Blog** con editor enriquecido (H1 a H3, negrita, cursiva, subrayado, links e imágenes subidas a R2), borradores, portadas y reordenar secciones arrastrando.
- 👤 **Sobre mí**: tu historia, las cards de experiencia y tus publicaciones (citas de artículos), editables inline como admin.
- 🧪 **Proyectos**: cards y páginas de detalle. El texto de cada proyecto usa el mismo editor que el blog.
- 💸 **Contratar**: qué puedo hacer (agentes de IA y automatizaciones) y un formulario simple (nombre, email y mensaje de hasta 1000 caracteres) que te llega por mail.
- 🌗 Tema claro y oscuro, 🇦🇷/🇺🇸 español e inglés.
- 🔐 Login con Google para cualquiera; admin solo los emails que permitas.
- 🤝 **Referidos**: cualquiera con cuenta de Google crea su código y gana el 15% de lo que abone el cliente que traiga; registro de pagos para el admin.
- 🎛️ Panel "Personalizar" (foto de perfil del header, solo admin): secciones, colores, info personal y proyectos, todo guardado en D1.
- 📊 **Visitas**: Cloudflare Web Analytics (sin cookies) más un contador propio en D1, también sin cookies ni IP. El admin las ve en `/admin/visitas` (menú de la foto de perfil), con visitas por día, por origen y links UTM listos para Instagram, LinkedIn, X y email.

## 🧰 Stack

- [Next.js](https://nextjs.org) (App Router), compilado para Cloudflare con [OpenNext](https://opennext.js.org/cloudflare)
- [Cloudflare Workers](https://developers.cloudflare.com/workers/) + **D1** (SQLite) + **R2** (imágenes y archivos) + Rate Limiting + [Web Analytics](https://developers.cloudflare.com/web-analytics/)
- [Better Auth](https://www.better-auth.com) con login de Google
- [Resend](https://resend.com) para el mail del formulario (con `send_email` de Cloudflare Email Routing como respaldo)
- Tailwind CSS 4, TypeScript y `tsx --test` para los tests

## 🚀 Arranque rápido

Necesitás **Node.js 24.22.1+** (la última LTS; está en `.nvmrc`, corré `nvm use`) y una cuenta gratis de Cloudflare (solo para publicar). Te recomiendo **pnpm** (está fijado en `package.json`); npm también funciona.

```bash
# 1. Instalar
pnpm install                  # o: npm install

# 2. Variables (secretos locales, ignorados por git)
cp .dev.vars.example .dev.vars
# completá BETTER_AUTH_SECRET, GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, TURNSTILE_SECRET_KEY (RESEND_API_KEY es opcional; MCP_SERVICE_TOKEN solo para /api/mcp)

# 3. Base local (D1 en .wrangler/state) + posts de ejemplo
pnpm db:migrate:local         # o: npm run db:migrate:local
pnpm seed:blog                # o: npm run seed:blog

# 4. Correrlo
pnpm dev                      # o: npm run dev  → http://localhost:3000
```

### ☁️ Publicar en Cloudflare

1. `npx wrangler login`
2. Creá tus recursos y poné nombres/ids en `wrangler.jsonc`:
   - `npx wrangler d1 create <tu-db>` (copiá el `database_id`)
   - `npx wrangler r2 bucket create <tu-bucket>` (`MEDIA`). `BLOG_ASSETS` en este deploy apunta al bucket que ya existe, `serpix-assets`: no lo crees. Si forkeás, poné tu bucket o sacá el binding
   - cambiá `name`, `routes` (tu dominio), el destino de `send_email` y `vars` (`CONTACT_TO`, `CONTACT_FROM`, `CONTACT_INBOX`)
3. `pnpm db:migrate:remote` (el script usa el binding `DB` de `wrangler.jsonc`, no el nombre de la base: no hace falta tocar `package.json`)
4. Secrets: `npx wrangler secret put BETTER_AUTH_SECRET` (igual para los de Google, `TURNSTILE_SECRET_KEY`, `RESEND_API_KEY` y, para el MCP, `MCP_SERVICE_TOKEN`)
5. `pnpm run deploy` (si falla una vez, volvé a correrlo)

## 🎨 Hacelo tuyo

**Primero esto** 👇
- `src/content/site.ts`: secciones del menú y la site key pública de Turnstile. El nombre, las redes, los gustos, la agenda y los colores viven en D1 (`site_settings`, migración `0013`) y se editan en el modo admin (`PUT /api/settings`). Sin filas, el sitio usa defaults neutros (`DEFAULT_SITE` en `src/lib/site-settings.ts`).
- `src/lib/auth/admin.ts`: `ADMIN_EMAILS`, las únicas cuentas de Google que pueden editar. Cualquier otra cuenta puede ingresar, pero es un usuario común: sin modo edición, sin admin, sin borradores (todas las APIs de admin responden 401/403), y solo ve su propio panel de referidos.
- `src/lib/auth/options.ts`: `ALLOWED_HOSTS` y `TRUSTED_ORIGINS` (tus dominios, si no el login los rechaza).
- `public/`: reemplazá las fotos (`avatar*.jpg`), imágenes de proyectos y logos.
- Ícono del sitio (favicon, Apple Touch, PWA): monograma «lx» sobre fondo negro a sangre; la «l» va en degradé vertical amarillo `#F6CD35` (arriba) a naranja `#E2781B` (abajo). El master vectorial es `brand/lulox-logo.v5.svg` (`linearGradient`); el PNG recalculado está en `brand/lulox-logo-master.png`. `python3 scripts/make-icons.py` genera los PNG opacos de Apple Touch y PWA en `public/icons`; el favicon de pestaña (transparente, recortado) lo genera `python3 scripts/make-tab-favicon.py`. Nombres con versión `.v5` para refrescar cachés (`public/manifest.v5.webmanifest`, fondo y tema `#000000`). Copia canónica en R2: https://assets.lulox.com.ar/lulox/logo/v2/. Si forkeás, reemplazá `brand/` y corré los scripts.
- `public/og.png`: la imagen para compartir (og:image/twitter:image, 1200x630), recorte desde arriba de `avatar-hero.jpg`. Si cambiás la foto, regenerala. Los posts con portada usan su propia portada.
- **URLs en dos idiomas:** el español vive en la raíz y el inglés bajo `/en` con rutas traducidas: `/` ↔ `/en`, `/contratar` ↔ `/en/hire`, `/sobre-mi` ↔ `/en/about`, `/proyectos(/<id>)` ↔ `/en/projects(/<id>)`, `/contacto` ↔ `/en/contact`, `/privacidad` ↔ `/en/privacy`, `/blog` ↔ `/en/blog`, `/blog/<slug>` ↔ `/en/blog/<slug_en>`, `/ingresar` ↔ `/en/sign-in`, `/referidos` ↔ `/en/referrals`, `/servicios` ↔ `/en/services`, `/servicios/<slug>` ↔ `/en/services/<slug-en>` y `/casos(/<slug>)` ↔ `/en/case-studies(/<slug-en>)` (slugs traducidos en `SUBSEGMENTS_ES_TO_EN`) (`/en/tastes` y `/en/gustos` van a `/en/about`). **El idioma lo define la URL**, para el contenido y para la metadata: `src/proxy.ts` pone el header `x-lulox-locale` según la ruta (pisa el que mande el cliente) y reescribe `/en/...` a la página en español que la renderiza. La cookie `lulox-locale` solo guarda lo último que elegiste en el selector; no se usa para redirigir ni para elegir idioma (tampoco `Accept-Language`). El selector lleva a la misma página en el otro idioma (en un artículo, a su otro slug, leyendo el `hreflang` de la página). El mapa vive en `src/lib/routes.ts` (`SEGMENTS_ES_TO_EN`); los links internos se escriben en español y pasan por `href()` de `useLocale()`. Las URLs viejas en inglés de la raíz (`/about`, `/projects`, `/contact`, `/privacy`, `/login`) siguen redirigiendo igual que antes a las españolas.
- **Tarjetas para compartir (SEO):** cada URL tiene su `og:title`, `og:description`, `twitter:*`, `og:url` y `canonical` propios, en el idioma de la URL: `og:locale` `es_AR` en la raíz y `en_US` bajo `/en` (no dependen de cookies ni de `Accept-Language`). Cada página lleva `hreflang` `es-AR`, `en-US` y `x-default` (= español), y `sitemap.xml` lista las dos versiones de cada página con sus alternates. Formato "Página | {nombre}"; la home tiene título, descripción y keywords fijos de la propuesta en `src/content/home-copy.ts` (`meta`, ES y EN), no la descripción de D1. Los artículos usan su título y su `summary` en ese idioma (si falta el resumen, el comienzo del artículo); las demás páginas tienen su descripción corta propia en cada idioma. El helper está en `src/lib/page-metadata.ts` (`pageMetadata("/ruta-en-español", { es, en })`); el texto de cada ruta vive en su `layout.tsx` (o en `privacidad/page.tsx`). Si agregás una ruta, sumala a `SEGMENTS_ES_TO_EN` y dale su `pageMetadata(...)`.
- `wrangler.jsonc` y el link del footer en `src/components/views/home-view.tsx`.

### McpRpc

`lulox-mcp` habla con este Worker solo por un service binding al entrypoint `McpRpc` (`export class McpRpc extends WorkerEntrypoint` en `worker.ts`). No va montado en el `fetch` por defecto: el redirect de `www`, el 404 de escaneos y el rate limit no corren en esa llamada. Cada método arma un `Request` interno a `https://lulox.com.ar/api/mcp/*` con `Authorization: Bearer <MCP_SERVICE_TOKEN>` y se lo pasa al handler de OpenNext (`handler.fetch`). La traducción a `RpcResult` (`{ok:true, data}` o `{ok:false, error:{code, message}}`) está en `src/lib/mcp-rpc.ts`, sin importar `cloudflare:workers`.

| Método | Pedido interno | Si sale bien |
|---|---|---|
| `uploadImage({filename?, contentBase64})` | `POST /api/mcp/media` con JSON (`contentBase64` en el body que ya acepta la ruta) | `{url, key}` |
| `createDraft({title, summary, body, slug?, tags?, topics?, coverImage?, images?, slides?})` | `POST /api/mcp/posts` | `{slug, slugEn, published: false, needsTranslation, previewUrl}` |
| `publishPost({slug, confirm})` | `POST /api/mcp/posts/<slug>/publish` con `{confirm: true}` | `{slug, slugEn, published: true, alreadyPublished}` |
| `listPosts({drafts?})` | `GET /api/mcp/posts`, o `?drafts=1` si `drafts` es el booleano `true` | `{items}` |
| `getPost({slug})` | `GET /api/mcp/posts/<slug>` | el post, o `not_found` si no está |

`confirm` tiene que ser el booleano `true`. Si falta, es `false` o es el string `"true"`, la respuesta es `invalid` con mensaje `confirm_required` y no se llama a la ruta. Sin `MCP_SERVICE_TOKEN` (o solo espacios) es `not_enabled` con mensaje `blog MCP not configured`, también sin llamar. Mapeo del HTTP: 2xx pasa el JSON sin el campo `ok`; 400 y 409 son `invalid` (el mensaje es el código, por ejemplo `slug_taken`); 404 es `not_found`; 401 y 503 son `not_enabled` (`blog MCP not configured`); el resto es `internal` con un mensaje genérico. Ese mensaje no incluye stack, SQL ni el secreto.

### 🖱️ Convención de cursor

Todo lo clickeable muestra `cursor: pointer` y lo deshabilitado `cursor: not-allowed`. Lo resuelve una regla global al final de `src/app/globals.css` (links, botones, roles ARIA clickeables, `label[for]`, `select`, `summary`, inputs tipo range/checkbox/radio/submit/file/color y sus thumbs), así que componentes nuevos no necesitan nada extra. Excepciones a propósito: `.sec-reorder-handle` (`grab`) y `.md-acc-btn-edit` (contenedor editable). Para chequearlo: con `pnpm dev` corriendo, `pnpm audit:cursor` recorre todas las rutas en español y bajo `/en` (home, blog y artículos, contratar, sobre mí, proyectos, contacto, tastes, rothko, privacidad, ingresar, 404) en claro/oscuro con Chrome headless y falla si algo clickeable no tiene el cursor correcto (`AUDIT_URL`, `AUDIT_ROUTES`, `AUDIT_WAIT=load` para apuntar a otro sitio). Para recorrerlo como admin, pasale una sesión local con `AUDIT_COOKIE="better-auth.session_token=..."` (solo contra tu preview local). Los campos de escribir (texto, número, búsqueda, fecha) mantienen el cursor de texto.
